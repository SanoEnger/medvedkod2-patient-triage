# МедВед.Код2 · только backend

Общий запуск frontend + API + PostgreSQL одной командой: [Docker](../../docs/DOCKER.md).

Самостоятельная часть FastAPI для интеграции в monorepo `SanoEnger/medvedkod2-patient-triage`.
API подключён к PostgreSQL; JSON хранится зашифрованным, сервер принимает HTTPS. Настройка БД, сертификатов и ключей: [README_POSTGRES.md](README_POSTGRES.md). Это не production medical device: только синтетические кейсы хакатона.

## Состав

- `app/main.py` — FastAPI, Swagger /docs, OpenAPI /openapi.json, заголовки безопасности, CORS.
- `app/api/routes.py` — REST API, авторизация и endpoints опроса.
- `app/core/` — конфигурация из окружения, подписанные короткоживущие bearer-токены.
- `app/integrations/max_core.py` — только server-to-server проверка 5-минутного JWT организаторов по `/api/v3/users/user-for-external-service`.
- `app/services/safety.py` — детерминированная проверка экстренных признаков после каждого ответа, независимая от LLM.
- `app/services/sessions.py` — опрос, возврат, пересчёт, идемпотентность, TTL, результат.
- `app/schemas/survey.py` — Pydantic v2.
- `tests/test_backend.py` — офлайн-тесты на synthetic input.

## Запуск (Python 3.12+)

Из папки `apps/api`:

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
pip install -r requirements-backend.txt
```

Подготовьте PostgreSQL и сертификаты по [инструкции подключения](README_POSTGRES.md), примените миграции, затем запустите:

```powershell
.\run_demo.ps1
```

Swagger UI: https://localhost:8443/docs. Локальному браузеру нужно доверие к созданному CA. Backend-тесты: python -m pytest -q. Для проверки хранения, миграций и TLS нужны переменные отдельной тестовой БД из инструкции.

Для реального MAX launch дополнительно задайте на сервере `CORE_SERVICE_TOKEN` из выданных организаторами секретов и установите `DEMO_MODE=false`. Описание всех переменных в `.env.backend.example`. **Сервисный токен никуда не отдаётся фронтенду.**

## Контракт авторизации

1. Фронтенд получает JWT из адреса `?token=...` и отправляет `POST /api/v1/auth/launch` с JSON `{"mode":"host","host_token":"<JWT>"}`.
2. Backend вызывает `GET https://tm-test-yakut.hostco.ru/api/v3/users/user-for-external-service?token=...` с `Authorization: Bearer <CORE_SERVICE_TOKEN>`.
3. Backend проверяет ответ и использует только `_id`, не сохраняет и не выдаёт СНИЛС, ОМС, дату рождения, ФИО, телефон.
4. Backend возвращает **свой** `access_token` на час; остальные запросы: `Authorization: Bearer <access_token>`.
5. После exchange фронтенд должен убрать token из адресной строки с `history.replaceState` и не логировать его. Не отправлять сюда `initDataUnsafe` вместо JWT.

### Контракт опроса

| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | Статус |
| POST | `/api/v1/auth/launch` | Проверка launch / demo |
| POST | `/api/v1/sessions` | `{"accepted_disclaimer":true}` |
| GET | `/api/v1/sessions/{id}` | Текущий шаг, прогресс, состояние |
| POST | `/api/v1/sessions/{id}/answers` | `{question_key, value, idempotency_key}` |
| POST | `/api/v1/sessions/{id}/back` | `{target_step}`; индекс с нуля, стирает следующие ответы |
| POST | `/api/v1/sessions/{id}/triage` | Карточка срочности, если достаточно проверенных правил |
| DELETE | `/api/v1/sessions/{id}` | Удаление демо-сессии |

Порядок `question_key`:
`primary_complaint` → `patient_context` → `symptom_details` → `red_flags` → `medical_history`.
Схемы каждого `value` и примеры доступны через Swagger / OpenAPI. При экстренном флаге любой ответ немедленно переводит сессию в `EMERGENCY_STOP`, возвращает 103/112 и не вызывает модель. Возврат из этого состояния запрещён: нужна новая безопасная сессия. Повтор с прежним `idempotency_key` возвращает прежний ответ, а с другим телом возвращает 409.

### Быстрая проверка без MAX

```bash
curl.exe --cacert ../../.local/runtime/ca.crt -s -X POST https://localhost:8443/api/v1/auth/launch -H "Content-Type: application/json" -d '{"mode":"demo"}'
```

Возьмите `access_token`, подставьте его в заголовок `Authorization: Bearer ...`, создайте сессию и отправьте первый ответ:

```json
{"question_key":"primary_complaint", "value":{"category":"breathing", "text":"одышка в покое"}, "idempotency_key":"00000000-0000-4000-8000-000000000001"}
```

Ожидается `EMERGENCY_STOP`, `RF_DYSPNEA_REST`, 103/112.

## Границы, важные до интеграции

- API использует PostgreSQL: перезапуск сохраняет опрос и идемпотентность. Результаты вынесены в triage_results с версиями правил; изменения фиксируются в audit_events. JSON ответов, состояния, переписки, результатов, predicates и meta зашифрован AES-256-GCM. История пока доступна только через операции слоя БД; React и отдельные HTTP-методы истории здесь не добавляются.
- NLP-модуль вызывается для свободных жалоб после pre-safety, вне транзакции БД; после ответа выполняется post-safety. Его результат не меняет срочность. `NLP_MODE=mock` — автономный режим, `live` — Groq. NLP и ревизия сохраняются в зашифрованном состоянии PostgreSQL. Поздний ответ после возврата/изменения шага отбрасывается.
- Для обычных случаев результат `UNKNOWN`, за исключением одного узкого синтетического `DEMO_SKIN_MILD_V0` с `PLANNED`. P1/P3 и клинические шаблоны не утверждены, поэтому самопомощь и несуществующие диагнозы не выдаются.
- Лексический поиск ограничен. Это **не** медицинский триаж для реальных пациентов. Признаки T01–T10 протестированы только на синтетических формулировках; врач/ментор должен утвердить правила до реальных пользователей.
- Сервис выдаёт собственные HMAC токены без списка отзыва. Для production желательно server-side session store / rotation / shared throttling на proxy. Локальный auth launch ограничен 20 попытками в минуту на IP в рамках одного процесса. TTL демо-сессий максимум 24 ч, cleanup выполняется API раз в минуту, реальных медицинских данных не принимать.
- CSP `FRAME_ANCESTORS` и `CORS_ORIGINS` согласовать с MAX-host. Встроенному iframe не гарантирован доступ к cookie, поэтому выбран bearer header вместо cookie (CSRF для cookie здесь не нужен). В production HTTPS обязателен.
- Не коммитить `.env`, сервисные токены, user JWT, Groq key, реальные медицинские данные. Секреты, жалобы и данные пользователя не логируются кодом приложения.
- Пользовательское имя, возраст, пол и номер полиса из Core **не** используются/не сохраняются. Для детского температурного правила возраст в форме **синтетический**, а не дата рождения из Core.

## Необязательные поля опросника

patient_context поддерживает lactation: boolean | null. medical_history поддерживает hospitalizations_last_year: list[str] с теми же ограничениями, что и операции: до 10 записей по 120 символов. Старые запросы остаются допустимыми; новые поля сохраняются в существующем зашифрованном JSON ответов. Правила срочности не менялись.

## Чат

`NLP_MODE=mock` использует фиксированный локальный ответ чата и не отправляет
переписку в Groq. `NLP_MODE=live` использует настроенную модель Groq. При экстренном
сигнале от правил или модели выводится единый текст с 103/112. Схема проверяет
формат ответа; медицинская корректность свободного текста модели требует отдельной
проверки на синтетических сценариях и не гарантируется системным prompt.

Все методы требуют того же bearer-токена, что опрос.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/chats/availability` | Активный опрос владельца либо `null`; ответы позволяют продолжить опрос после перезагрузки |
| GET | `/api/v1/chats` | История владельца. `limit` от 1 до 100 (по умолчанию 20), `cursor` из `next_cursor` предыдущей страницы |
| POST | `/api/v1/chats` | `{accepted_disclaimer:true, questionnaire_id?:UUID}` — отдельный чат либо уточнение завершённого опроса |
| GET | `/api/v1/chats/{id}` | Сообщения, результат, `pending`, `retryable` |
| POST | `/api/v1/chats/{id}/messages` | `{text, client_message_id:UUID}`; до 2000 символов, повтор ID не создаёт дублей |
| DELETE | `/api/v1/chats/{id}` | Удаление чата. Для чата по опросу удаляются также ответы и результат |

Список возвращает `items` и `next_cursor`. Элемент содержит ID, тип (`chat`
для отдельного чата, `questionnaire` для переписки по опросу,
`questionnaire_result` для результата завершённого опроса без сообщений
пользователя), заголовок по теме, даты создания, последней активности
и истечения срока, признак экстренной остановки. Результат без переписки
открывается и удаляется через `/api/v1/sessions/{id}`. Сортировка по убыванию
активности и ID. Если диалог обновился между страницами, он может переместиться
выше курсора и появится при обновлении списка. `next_cursor: null` означает
конец списка. Схемы и параметры описаны в `/openapi.json`.

Сервер подбирает заголовок по первым трём сообщениям пользователя и, для опроса,
по основной жалобе и описанию симптомов. Например, «Боль в колене». В заголовке
используется стандартная формулировка темы. Тип записи передаётся отдельно.

Активный опрос не блокирует чтение истории. Чужие, удалённые и просроченные
чаты возвращают одинаковый 404 для открытия, отправки и удаления. При ошибке
аутентификации шифротекста API возвращает 503 с `chat_storage_unavailable`.
Ответы истории и чатов содержат `Cache-Control: no-store`. Просмотр не меняет TTL.

Создание и отправка блокируются с 409, пока есть незавершённый опрос. Внешний вызов выполняется после фиксации сообщения, без удержания транзакции БД. Неоконченная попытка может быть повторена после освобождения обработки (`retryable=true`). Ограничения: 100 пар сообщений, последние 20 сообщений до 12000 символов в контексте модели, общий TTL обращения до 24 часов. Сообщения и контекст хранятся зашифрованными; в Groq передаётся расшифрованный JSON по HTTPS.

Для `NLP_MODE=live` нужны серверные `GROQ_API_KEY` и `GROQ_MODEL`. При сбое провайдера API возвращает 503. Детерминированная проверка экстренных признаков предшествует обращению к модели.
